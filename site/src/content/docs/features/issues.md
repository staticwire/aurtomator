---
title: Issues
---

The job `issues` runs in every run in which `check` succeeded, after `publish` when `publish` runs. It reads the final statuses: those of `publish` when it ran, and those of `check` otherwise. Its name is `status`, so the page of the run lists it as `check-updates / status`.

Before it touches an issue, the job writes the summary of the run to `$GITHUB_STEP_SUMMARY`, and the page of the run shows it under `check-updates / status summary`. The summary counts the packages and the ones up to date, lists every other package in a table with the label of the package table of the README, and shows the error of each failed package in a code block, as its issue does. `run_summary` and `status_label` in `scripts/lib/status.sh` write it, and `update-readme.sh` takes its labels from `status_label` too.

The step `Create issues` runs with `if: always()`. When a package failed, is held, has an alert in `.status/_alerts` or a line in `.status/_without`, or a newer aurtomator release is out, it first reads `has_issues` of the repository. `gh issue list` fails in a repository with Issues turned off, so when GitHub answers `false`, the step prints a notice and opens no issue. Any other answer goes on, and a failure to read the answer or to list the issues fails the step.

For every `.status/` entry with `check_failed:` or `update_failed:`, the step:

1. Creates the `auto-update` label when it is missing.
2. Skips the package when an open `auto-update` issue already has the title `❌ <package>: check failed` or `❌ <package>: update failed`, so a package never gets a second issue while one is open. The step compares the titles of up to 1000 open issues and uses no search, because a search splits `foo-bar` into words and finds the issue of `foo-bar` for `foo`.
3. Opens an issue titled `❌ <package>: check failed` or `❌ <package>: update failed`, after the status, with the package, the status, a link to the run and the error. The error holds text from upstream, a rejected tag name for example, so it stands in a code block, where links, images and mentions do not render, and is cut to its last 4000 characters. The body comes from `failure_issue_body` in `scripts/lib/issue.sh`.

When the checks of 5 or more packages failed on one host, `HOST_ISSUE_MIN` in `scripts/lib/issue.sh`, those packages share one issue instead. The host is that of the first `http://` or `https://` URL in the error, the URL that `http_get` could not read or that git could not reach, in lower case and without the port. `failure_host` reads it, and `failed_hosts` lists the hosts with their packages. The issue is titled `❌ <host>: <count> packages failed to check`, with the label `auto-update`, unless an open `auto-update` issue has that title for the host with any count. The body comes from `host_issue_body`: the host, a link to the run, and each package with its error in a code block. The errors share 50000 characters, at most 4000 each, so the body stays under the 65536 characters that GitHub accepts. A later run edits neither the title nor the body of an open host issue. An error without a URL, such as a timeout outside a request, always gets the issue of its package, and so does every failed update. The error of a check that ran out of its budget during a request names the URL of that request, and so does the error of a request to a silent host ([Update process](/aurtomator/internals/update-process/)), so both count for their host. `api.github.com` and `github.com` are two hosts.

An alert opens an issue as well, see [Update alerts](/aurtomator/features/update-alerts/). Its notes come from `.status/_alerts`, where `check-all.sh` writes one line for each alert that fired: the package, `hold` or `notice`, and the note, split by tabs. The body comes from `alert_issue_body` in `scripts/lib/issue.sh`.

- A `held:` status opens an issue titled `✋ <package>: update held` with the label `update-held`, unless an open `update-held` issue has that title. The body holds the held version and the notes of every alert that fired, in a code block, and asks the maintainer to publish the version by hand and set `current`.
- An `updated:` or `downgrade:` status of a package with a line in `.status/_alerts` opens an issue titled `🔔 <package>: <version> notice` with the label `update-notice`, unless an open `update-notice` issue has that title. The body holds the published version and the notes, in a code block. The maintainer closes it once the edit is done.

A line of `.status/_without`, which `publish` writes for a package that it published without some arches, opens an issue titled `⚠️ <package>: <version> without <arches>` with the label `arch-missing`, unless an open `arch-missing` issue has a title that starts with `⚠️ <package>: `, so a package has one such issue while any arch is out, whatever version it names. The body comes from `arch_issue_body`: the package, the version, the missing arches and a link to the run. See [Versions without some arches](/aurtomator/features/missing-arches/).

A newer aurtomator release, `newer: <release>` in `.status/_upstream`, opens an issue titled `🚀 aurtomator <release> available` with the label `aurtomator-update`, unless an open `aurtomator-update` issue has that title. The body comes from `upstream_issue_body`: the release, the version the run uses, the update through Dependabot, the update of `aurtomator.sh` by the first run on the new pin, and links to the release notes, to the manual update in SETUP.md and to the run. See [Updates of aurtomator](/aurtomator/features/aurtomator-updates/).

The step creates each label the first time it needs it and lists the open issues of each label once. When GitHub refuses an issue, the step prints a warning with the error of `gh` and goes on.

The job runs also when the package table stays the same, so an issue follows the statuses of every run. A package that starts failing gets its issue in that run, and an issue closed while the package still fails comes back in the next run.

The step before it, `Close resolved issues`, closes the issue of a package that recovered, with a comment that names the run and shows the new status in a code block, as the issue body shows the error. An open `❌ <package>: check failed` closes when the status is anything but `check_failed`. An open `❌ <package>: update failed` closes when the status is `up_to_date`, `updated`, `downgrade`, `rebuilt` or `arch_added`, so the version is in the AUR. An open `✋ <package>: update held` closes on the same statuses, so a failed check keeps it open. An open `❌ <host>: <count> packages failed to check` closes when fewer than 5 packages of the host failed to check, with the comment ``Fewer than 5 packages of `<host>` failed to check in <url>.``, and each of those packages that still fails gets an issue of its own in `Create issues` of the same run. An open `🚀 aurtomator <release> available` closes when `.status/_upstream` holds anything but `newer: <release>`: `VERSION` at the pin has reached the latest release, or a newer one is out and gets its own issue. A run without `.status/_upstream` closes none of them. An open `⚠️ <package>: <version> without <arches>` closes when `.status/_without` has no line for the package, with the comment ``Every arch of `<package>` is back as of <url>.``, and a run without `.status/_without`, which `publish` writes, closes none of them. An open `❌ Check AUR Package Updates failed`, which [Failed runs](#failed-runs) opens, closes with the comment `Run <url> succeeded.` when `prepare` and `verify` succeeded or were skipped, since the step itself runs only after a `check` that succeeded and a `publish` that succeeded or was skipped. The close step comes first because an open issue of a package holds back a new one: a package whose check passes and whose update fails gets its check issue closed and an update issue opened in the same run. It runs neither after a failed step nor after a failed `publish`, so a status that `publish` did not write closes nothing, and with Issues turned off it does nothing.

## Failed runs

The job `issues` reports failed packages, and a run that fails in `image` or `check` never reaches it. Your calling workflow has a second job for that case, `notify`, with `needs: check-updates` and `if: ${{ always() && needs.check-updates.result != 'success' }}`. It calls the reusable `notify-failure.yml` at the same pin and grants `actions: read` to list the jobs of the run and `issues: write`. The condition lets `notify` run after every result but `success`, and its one step, `Open an issue for the failed run`, decides from the jobs of the run.

The step lists the jobs of the run and takes those with the conclusion `failure` or `timed_out`. It opens one issue titled `❌ Check AUR Package Updates failed`, with a link to the run, its branch and the names of those jobs, and opens no second one while that issue is open. The next run without a failed job closes it, see [Issues](/aurtomator/features/issues/), and a later failure then opens a new one. When the list names no such job, the run was canceled: the step prints the notice `No job of the run failed, so the canceled run gets no issue` and opens nothing. When the list cannot be read, the issue says `jobs that could not be listed` in place of the names. The branch stands in a code span whose fence is longer than any run of backticks in its name, so a backtick in the name cannot end the span and turn the text after it into a mention. A repository with Issues turned off gets a notice instead, as in [Issues](/aurtomator/features/issues/). The job runs on `ubuntu-latest` with a 5-minute timeout and checks out nothing.

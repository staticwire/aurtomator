---
title: Update process
---

`check-all.sh --update` calls `update-pkg.sh` for every package with a new version. `--prepare`, `--verify` and `--publish` split the same update into three runs, see [Prepare and publish](#prepare-and-publish).

Outside `--update`, `check-all.sh` gives each package a time budget: 120 seconds for `check-update.sh`, and 300 seconds each for `update-pkg.sh`, `verify-pkg.sh` and `publish-pkg.sh`. `timeout` ends the script together with everything it started, makepkg, git and curl included, and the package gets `check_failed: timed out after 120 s` or `update_failed: timed out after 300 s`. The status of a check that ran out of its budget during a request names the URL of that request, as in `check_failed: https://github.com/owner/repo.git: timed out after 120 s`. `AURTOMATOR_CHECK_TIMEOUT` and `AURTOMATOR_UPDATE_TIMEOUT` change the budgets. `--update` has none, because it runs on a terminal, where git and ssh may ask for a passphrase, and a command under `timeout` cannot read the terminal.

Without a mode and with `--update`, a package whose check failed within its budget is checked once more after all the others, following a pause of 60 seconds, and the second result counts. A check that ran out of its budget is not repeated, and neither is a check that failed on a host that did not answer, so a run without network does not take twice as long. `AURTOMATOR_RECHECK_DELAY` changes the pause, and the tests set it to 0.

In the same two modes `check-all.sh` keeps a memory of silent hosts, the hosts that did not answer in the run. The memory is a temporary directory: `check-all.sh` exports its path as `AURTOMATOR_HOSTS_DIR` and removes it at the end of the run. A host goes into the memory when curl ends a request of `http_get` with exit 28 and the status `000`, a timeout without any answer. It goes in as well when a check runs out of its budget during a request to the host and one HEAD request of 10 seconds from `check-all.sh` then times out without a status. For git, that HEAD request asks `<repository>/info/refs?service=git-upload-pack`, the first URL that git asks itself. A later request of the run to a silent host fails at once with `<url>: <host> did not answer earlier in this run`, so a silent host costs the run one check, whatever the number of its packages.

A refused connection, a failed DNS lookup, an HTTP error and an answer that stops halfway leave the host out of the memory. A redirect to a silent host leaves it out as well, because curl reports the status of the redirect. `http_get`, `remote_tags`, the clone of `git-latest.sh`, `aur_clone` and `probe_url` read the memory. Without `AURTOMATOR_HOSTS_DIR` they send every request, as in a run of `check-update.sh` on its own. In `--prepare`, `--verify` and `--publish`, which run no strategy, `check-all.sh` removes the variable before it starts their scripts. The memory leaves out a URL with a user name or a port, such as `https://git.example.com:8443/`: curl contacts another host or port than the bare name, so such a request neither fails at once nor puts a host into the memory.

## Arguments

```text
update-pkg.sh <package-name> <new-version> [--asset <value>] [--arch-out <arches>] [--dry-run] [--prepare <dir>]
verify-pkg.sh <package-name> <version> <prepared-dir> [--asset <value>] [--arch-out <arches>]
publish-pkg.sh <package-name> <version> <prepared-dir> [--asset <value>] [--arch-out <arches>] [--dry-run]
check-asset.sh <package-name> <pkgver>
check-arch.sh <package-name> <version> [--asset <value>]
check-all.sh [--update | --prepare <dir> | --verify <dir> | --publish <dir>] [--dry-run]
```

## Step-by-step

1. Read `.aurtomator.conf` when it exists, as data, see [Configuration file](/setup/#configuration-file). In CI, `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL` and `GPG_KEY_ID` come from the workflow environment.
2. Wait 2 seconds, then clone `ssh://aur@aur.archlinux.org/<package-name>.git` into a temporary directory, with up to 3 attempts 5 seconds apart. A clone without a PKGBUILD stops the update.
3. When the clone lands on a detached `HEAD`, reset `master` to `origin/master`, so the push is a fast-forward.
4. Warn when the PKGBUILD has no `# Maintainer:` line.
5. Audit the PKGBUILD. `pkgver()` with the wrong strategy and mixed checksums block the update. Patches and an `epoch` other than 0 only warn. See [Supported packages](/supported-packages/).
6. Set `pkgver` with `sed` and `pkgrel` to 1, or to the `pkgrel` of the AUR when the AUR has this version already, as for a package added without `current`. For a package with `upstream.asset_var`, also write the value of `--asset` to its line and set `pkgrel` as [Values from release asset names](/features/asset-values/) says. When `pkgver` and `pkgrel` of the AUR PKGBUILD already hold these values, read as bash reads them, so past quotes and a comment, the AUR already has this version: the script changes no line, writes the version to `current` and the value to `current_asset`, and exits with code 2. A dry run writes neither.
7. Validate every `http` and `https` source URL, whatever its checksum. Unless a checksum array holds a `SKIP` other than that of a signature and no remote source has a real hash, run `updpkgsums`, and verify the result with `makepkg --verifysource --skippgpcheck`. A signature is a source whose file name ends in `.sig`, `.sign` or `.asc`, and makepkg gives it `SKIP` itself. makepkg also gives `SKIP` to every `svn` source and to a `git`, `hg` or `bzr` source without the pin it hashes: `#commit=` or `#tag=` for git, `#tag=` or `#revision=` for hg, and `#revision=` for bzr. A `fossil` source is hashed as a download. Step 5 allows a real remote hash only next to such a `SKIP`, and `makepkg` clones the repository of a VCS source to run `updpkgsums`. Any failure stops the update.
8. Run `namcap` when it is installed. Errors stop the update. Warnings are printed.
9. Regenerate `.SRCINFO` with `makepkg --printsrcinfo`.
10. Check `PKGBUILD` and `.SRCINFO` against the files of the clone's `HEAD`, as publish does in steps 4 and 5 of [Prepare and publish](#prepare-and-publish). A refused file stops the update.
11. With `--dry-run`, print the PKGBUILD diff and stop.
12. Commit `PKGBUILD` and `.SRCINFO` as `<new-version> release from <strategy>`, or `<new-version>-<pkgrel> release from <strategy>` for a rebuild, authored by `GIT_AUTHOR_NAME` and `GIT_AUTHOR_EMAIL`, by default `aurtomator` and `aurtomator@users.noreply.github.com`. With `GPG_KEY_ID` set, the commit is amended with a signature. When signing fails, the commit is pushed unsigned.
13. Push, with up to 3 attempts 5 seconds apart.
14. Write `current`, `current_asset` for a package with `upstream.asset_var`, and `last_updated` to the package YAML.

`AURTOMATOR_CLONE_DELAY` and `AURTOMATOR_RETRY_DELAY` change the 2 and the 5 seconds. The tests set both to 0. The anonymous HTTPS clones of prepare and verify, see [Prepare and publish](#prepare-and-publish), start without the 2 seconds.

## Prepare and publish

A PKGBUILD is a bash script, and steps 5 and 7 to 9 of [Step-by-step](#step-by-step) execute it: the audit, the check of the source URLs, `updpkgsums`, `makepkg --verifysource`, `namcap` and `makepkg --printsrcinfo`. Whoever can push to the AUR repo of a tracked package, a co-maintainer for example, runs code in those steps. Prepare and publish split the update so that this code never runs where the SSH key, the GPG key or a write token is. Prepare runs a job of its own for each package, so that code reaches the prepared files and the status of its own package alone. Verify checks the checksums against the sources in between, and publish takes the statuses from the check run, which executes no PKGBUILD.

**Prepare**, `update-pkg.sh --prepare <dir>`, needs no secrets:

1. Clone `https://aur.archlinux.org/<package-name>.git` anonymously.
2. Run steps 3 to 9 of [Step-by-step](#step-by-step). With `--arch-out`, the update also changes the `arch=(...)` line, see [Versions without some arches](/features/missing-arches/).
3. Copy `PKGBUILD`, `.SRCINFO` and the commit id of the clone's `HEAD` to `<dir>/<package-name>/` as `PKGBUILD`, `.SRCINFO` and `base`. Nothing is committed and the package YAML does not change. Exit code 2 still means the AUR already has the version.

**Verify**, `verify-pkg.sh <package-name> <version> <dir>/<package-name>`, needs no secrets, never sources the PKGBUILD and never runs `makepkg`:

1. The prepared directory must pass step 1 of publish below.
2. Clone `https://aur.archlinux.org/<package-name>.git` anonymously with `--no-checkout`. When `HEAD` is not `base`, the AUR repo moved after the update was prepared: exit code 3. The entries at the top of `HEAD` are written to a separate directory with `git ls-tree` and `git cat-file`, so git applies none of the links, attributes or filters of the repo: a regular file with its content, a symlink as a link to nowhere, anything else as an empty directory. The steps below read the AUR copy there. Prepared `PKGBUILD` and `.SRCINFO` that equal those of the AUR copy change nothing, and the verify ends there with exit code 0.
3. `PKGBUILD` and `.SRCINFO` in the AUR copy must be regular files. When the AUR copy has `<version>`, the prepared files must be those of the AUR, as in step 3 of publish below, and verify has nothing to check; the files of the AUR for another version stop it with exit code 1. Otherwise the prepared files must hold no NUL byte and pass steps 4 and 5 of publish below, with `<version>` and, for a package with `upstream.asset_var`, the value of `--asset` as the asset value. Such a package needs `--asset`, and any other package refuses it. `check-all.sh --verify` passes the version and the asset value that the check run found, so a prepared update with another `pkgver` or asset value stops before anything is downloaded. From here on, every source URL in the prepared `.SRCINFO` follows from the AUR copy.
4. Each checksum array of the prepared `PKGBUILD` must hold the same values as the same key in the prepared `.SRCINFO`.
5. Every checksum other than `SKIP` must match its source, computed as makepkg does with `<algorithm>sum`. The file is the one makepkg uses. A file in the AUR repo with the name of the source comes first and must be a regular file. Otherwise a remote source is downloaded with curl, retried and with the cookie engine on as makepkg does, over `https` only, redirects included. The AUR copy picks the URL, so curl stops a download past 600 MiB and an attempt that stays below 100 KiB/s for 60 seconds. The downloads of one package take at most 1 GiB together: each download gets what the budget leaves, at most 600 MiB, and none starts once the budget is gone. A checksum of a download over `http` or `ftp` stops the verify: there the network path would pick the file, and with it the checksum, in prepare as in verify. A git source at `#tag=` or `#commit=` is fetched alone, that tag or commit without the history of the repository, over `https` only, and git follows a redirect only to `https`. A `#commit=` takes the full id of the commit, which the host must serve by that id, as GitHub does. The fetch counts toward the 1 GiB of the package once it ends. Its checksum is that of `git archive --format tar` of the tag or commit, with `export-subst` and `export-ignore` turned off, as makepkg computes it. A checksum for any other source, another VCS for example, cannot be checked and stops the verify.
6. Any mismatch stops the verify with exit code 1. Otherwise the exit code is 0.

**Publish**, `publish-pkg.sh <package-name> <version> <dir>/<package-name>`, never sources the PKGBUILD and never runs `makepkg`. It treats the prepared files as untrusted:

1. The prepared directory must not be a symlink, `PKGBUILD`, `.SRCINFO` and `base` must be regular files, and `base` a commit id.
2. Clone over SSH with `--no-checkout`, and write the AUR copy as step 2 of verify does. When `HEAD` is not `base`, the AUR repo moved after the update was prepared: exit code 3. `PKGBUILD` and `.SRCINFO` in the AUR copy must be regular files, not symlinks.
3. When the AUR copy has `<version>`, and for a package with `upstream.asset_var` the value of `--asset`, the prepared files must be those of the AUR, because `update-pkg.sh` hands them over then and only then: the publish ends with exit code 2 and sets `current`, and any other prepared files stop it with exit code 1. The files of the AUR for another version stop it as well. Otherwise the prepared `pkgver` must be `<version>`. `check-all.sh --publish` passes the version the check run found, and the prepare run was given the same one, so another `pkgver` stops the publish with exit code 1. With `--arch-out`, an update that changes the `arch=(...)` line goes on to step 4 at the version of the AUR too, and the files of the AUR stop it, see [Versions without some arches](/features/missing-arches/).
4. The prepared `PKGBUILD` may differ from the AUR copy only in `pkgver=`, which must be `<version>`, in `pkgrel=`, which must be `1`, or the `pkgrel` of the AUR copy when it has `<version>` already, and in the values of the checksum arrays. A package with `upstream.asset_var` may also change the value of that line, to the value of `--asset`, and takes `pkgrel` from [Values from release asset names](/features/asset-values/). The arrays keep their names and lengths, hold only quoted hex checksums or `SKIP`, and have a `SKIP` exactly where the AUR copy has one. They stand where the AUR copy has them, or in one block at the place of the first one and in any order, as `updpkgsums` writes them. Comments and line continuations may stand between the checksums, read as bash reads them: a `#` at the start of a line, right after the opening parenthesis, or after a space or a tab comments out the rest of the line, and a backslash that ends a line without a comment, as a word of its own, continues the array on the next line. A comment in or after an array, and an empty line inside one, must be one the arrays of the AUR copy hold, and no more often: `updpkgsums` writes none, so any other one would carry text from the prepare job into the commit. A backslash on the line that closes the array stops the publish, because bash joins the next line to the assignment. With `--arch-out`, the `arch=(...)` line and the checksum arrays of the arches the update takes out or puts back may differ as [Versions without some arches](/features/missing-arches/) says.
5. The prepared `.SRCINFO` must have as many lines as the AUR copy, not counting empty lines at the end: `makepkg --printsrcinfo` writes none, and some AUR copies end in one, as those `mksrcinfo` v8 wrote do. Each `source` line of the prepared `.SRCINFO`, with or without an arch suffix, must be the line of the AUR copy with the old version replaced by `<version>`. A source that is `SKIP` in every checksum array of its arch may also change the digits in the name it is saved under, the part before `::`, as `neovim-20261014.tar.gz` becomes `neovim-20261016.tar.gz` in a PKGBUILD that names a nightly download by `$(date -u +%Y%m%d)`. Its URL after `::` must still be the AUR URL with the version replaced. Verify never downloads a `SKIP` source, and makepkg takes the sources from the `PKGBUILD`. For a line that is not a source, `pkgver`, `pkgrel` or a checksum, the value of the line in the AUR copy, the part after ` = `, is looked up in the text of the AUR `PKGBUILD` without its `pkgver=` and `pkgrel=` lines, the line of `upstream.asset_var`, its checksum arrays and its comment lines, which start with `#` after any spaces or tabs. When that text holds the value, the prepared line must equal the line of the AUR copy: a license, a dependency or a description can hold the old version without taking it from `pkgver`, as `GPL-2.0` does in a package at version `2.0`. Otherwise the prepared line must be the line of the AUR copy with the version replaced in the same way, as `provides=("demo=${pkgver}")` gives `provides = demo=2.1` at version `2.1`. The replacement also covers three forms a PKGBUILD often derives from `pkgver`: dots and plus signs turned into underscores (`1_86_0`, and `28_21` of `28+21` in the asset names of Temurin early-access builds), the part before the first `+` (`0.13.0` of `0.13.0+dev+1853+g6edb38ca98`), and the version without its last component (`6.19` of `6.19.0`, as in `frameworks/${pkgver%.*}/` of KDE Frameworks). The last form counts only while it keeps a dot. With `pkgver_dash`, a form of the old or the new version with a dash in place of that character counts as the version, as `${pkgver//_/-}` writes `0.0.1-rc.20` for `0.0.1_rc.20`, and with `pkgver_dash: ''` a form with a dash between two of its characters, as `${pkgver/rc/-rc}` writes `2.5.0-rc1` for `2.5.0rc1`. With `pkgver_format`, the upstream version inside the old and the new version counts as a form too, as `${pkgver#4.}` writes `4215` for `4.4215`. Nothing else in the line may differ. Each part of a line is replaced at most once, so `5.1` inside an already replaced `5.10.0` stays. A form counts only where it does not continue another number, with no digit or dot before it and no digit after it, so with `pkgver=0.1` the `0.1` inside `libbar-10.1.tar.gz` stays. A line built from any other form of the version, a lone major version for example, stops the publish, and so does a line that has the version replaced in one place and kept in another. A source of another project whose version equals a form of the version stops it too when the bump changes that form, as `game-data-2.0.tar.gz` next to `pkgver=2.0.1` does on the bump to `2.1.0`, since it cannot be told from a directory derived from `pkgver`. The package then needs a manual update. `pkgver` must be `<version>`, and `pkgrel` and the checksums follow the rules of step 4. When `pkgver` changes and a download over `http`, `https` or `ftp` has a real checksum, or a VCS source is pinned by `#commit=`, `#tag=` or `#revision=`, at least one source URL, the part after `::`, or one checksum has to change as well, for each architecture: the common sources and checksums count for every architecture, and those of `source_<arch>` for that architecture. Otherwise the new version would hold the files of the old one, as it would with `pkgver="${_pkgver//-/.}"` and sources built from `_pkgver`, with a download URL without the version whose file has not changed, with `#commit=$_commit` and a `_commit` the bump leaves alone, or with the archive of a fixed commit saved under a name that holds the version, as `pkgname-$pkgver.zip::$url/archive/$_commit.zip`. A download with a real checksum that is saved under a new name and keeps its URL and its checksum is refused even when another source changes, since it holds the old file. A VCS pin that stays is refused only when no other source or checksum changes, so a submodule pinned to a commit can stay while the main source moves, and a pin next to a file fetched from the tag passes. A VCS source without a pin, on its default branch or on `#branch=`, and a download with a `SKIP` checksum do not count, because makepkg fetches what they hold at build time. For a package with `upstream.asset_var`, each old asset value in a line stands for the new one, see [Values from release asset names](/features/asset-values/). With `--arch-out`, the lines of the arches the update takes out or puts back leave the two copies before this check, see [Versions without some arches](/features/missing-arches/).
6. Any other difference, and a NUL byte in either file, stops the publish with exit code 1. Otherwise the index of the clone takes the tree of `HEAD`, and the two prepared files enter it byte for byte through `git hash-object --no-filters` and `git update-index`, so the commit keeps every other file of the AUR repo. `git add` would pass them through the attributes of the AUR repo, and `working-tree-encoding=UTF-7` there turns `+AAo-` in a comment into a new line that the checks above never saw. Steps 12 to 14 of [Step-by-step](#step-by-step) follow, with the commit message and the YAML writes of [Versions without some arches](/features/missing-arches/) for the arches. Prepared files that equal the AUR copy pass without steps 3, 4 and 5 when its `pkgver`, read as bash reads it, so past quotes and a comment, is `<version>` and the line of `upstream.asset_var` holds the value of `--asset`: the YAML gets `current`, and `current_asset` for a package with `upstream.asset_var`, loses `arch_wait` and the arches of `arch_out` that `arch=()` names, and the exit code is 2. The prepare run hands over these files when the AUR has the version.

makepkg reads only the PKGBUILD. The AUR stores the description, the URL, the dependencies, the relations and the licenses from `.SRCINFO` and serves them on the package page and through its RPC interface, and yay parses the `.SRCINFO` of every package it clones. Code that runs in prepare writes the `.SRCINFO` of its package, and it comes from whoever can push to the AUR repo of that package, as the first paragraph of this section says. Step 5 therefore takes the form of each line other than `pkgver`, `pkgrel`, `source` and the checksums from the text of the PKGBUILD, which verify and publish read without running it. Code in prepare cannot keep `depends = foo>=1.2` where the PKGBUILD writes `depends=("foo>=${pkgver}")` for version `1.3`.

In three cases the text does not tell how makepkg writes a line that holds the version, and the update stops on a correct line: a value written with an escaped character, `{a,b}` or `$'...'`, a version taken from a variable that does not follow `pkgver`, and a value derived from `pkgver` whose text the PKGBUILD also writes elsewhere outside a comment line. A comment after code counts as text. Such a package needs a manual update, or a PKGBUILD that writes the value as plain text or derives it from `pkgver`, see [Lines the check cannot read from the PKGBUILD (BLOCKED)](/supported-packages/#lines-the-check-cannot-read-from-the-pkgbuild-blocked).

`check-all.sh --prepare <dir>` runs no strategy and needs no `GITHUB_TOKEN`. It takes the versions from the statuses that a check run, `check-all.sh` without a mode, wrote to `.status/` before it, and reads them before the first PKGBUILD runs. It prepares every package with `new_version`, `available_downgrade`, `new_build` or `arch_back` into `<dir>/prepared/` and copies the statuses to `<dir>/status/`. A package with `upstream.asset_regex` takes its asset value from `.status/_assets`, keeps `pending`, and becomes `check_failed` without a value, see [Values from release asset names](/features/asset-values/). A package with a line in `.status/_arches` gets the arches of that line as `--arch-out`, see [Versions without some arches](/features/missing-arches/). A downgrade of a package without `allow_downgrade: true` gets `downgrade_skipped` instead, and a version jump of a package without `allow_version_jump: true` gets `jump_skipped`, see [Downgrades and version jumps](/features/downgrades/). An update that an alert with `hold: true` fires on gets `held`, see [Update alerts](/features/update-alerts/), and an update in the cooldown of its package gets `cooldown`, see [Cooldown](/features/cooldown/). A failed preparation becomes `update_failed`, and a package without a status from the check run becomes `check_failed`. The other statuses stay as the check run wrote them.

`check-all.sh --verify <dir>` runs `verify-pkg.sh` for every package in `packages/` that has a directory in `<dir>/prepared/`, and runs no strategy. It takes the version and the asset value from the statuses of the check run in `.status/`, as `--publish` does: the version of `new_version`, `available_downgrade`, `new_build` or `arch_back`, for a package with `upstream.asset_regex` its value in `.status/_assets`, and the arches of its line in `.status/_arches` as `--arch-out`. Without them `verify-pkg.sh` does not run, and the package gets `update_failed: no new version from the check run` or `update_failed: no asset value from the check run`. A line of `.status/_arches` of another form or for another version gives `update_failed: invalid arch record from the check run`. An update that fails is removed from `<dir>/prepared/`, and its status in `<dir>/status/` becomes `update_failed`. Exit code 3 counts as a failure as well: the prepare run writes `base` for every package, so a moved AUR repo looks the same as a wrong `base`. The next run prepares the package again. No package starts after 20 minutes of the loop, `AURTOMATOR_VERIFY_BUDGET` in seconds, so the verify job ends within its 30 minutes even when the last package takes its 300 seconds. A package that did not start gets `update_failed: verify ran out of its 20 minutes in this run`, and the next run prepares it again.

`check-all.sh --publish <dir>` takes the statuses of the check run from `.status/`, as `--prepare` does, and writes `.status/` anew. `up_to_date`, `check_failed`, `downgrade_skipped`, `jump_skipped`, `held`, `pending` and `cooldown` stay as they are, and the alerts of a held update are evaluated again to record their notes in `.status/_alerts`. A downgrade of a package without `allow_downgrade: true` gets `downgrade_skipped`, a version jump of a package without `allow_version_jump: true` gets `jump_skipped`, an update that an alert with `hold: true` fires on gets `held`, an update in the cooldown of its package gets `cooldown`, and none of them is published. A missing status, and one the check run does not write, become `check_failed`. For a package with `new_version`, `available_downgrade`, `new_build` or `arch_back` and a directory in `<dir>/prepared/`, it publishes the version in that status, with the asset value from `.status/_assets` for a package with `upstream.asset_regex` and the arches of `.status/_arches` as `--arch-out`, and runs no strategy, so nothing contacts an upstream host while the AUR and GPG keys are in place. It writes `arch_wait` and `.status/_without` as [Versions without some arches](/features/missing-arches/) says. Exit code 3, an AUR repo that moved, leaves the status at `new_version`, `available_downgrade`, `new_build` or `arch_back` without an error, and the next run prepares the package again. A package with one of these statuses and no prepared directory gets the `update_failed` status that the prepare or the verify run wrote for it to `<dir>/status/`, or `update_failed: prepare and verify handed over no update`. A package that `.status/_deferred` names keeps its status without an error instead: the check run left it for a later run, past the 256 packages one run prepares. Nothing else is taken from `<dir>/status/`, and only a regular file without a NUL byte: the prepare run executes PKGBUILDs, and code from one of them writes the files of its package.
